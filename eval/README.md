# eval 回路 — 真实任务成功率度量

398 个合成测试只能保证"代码行为符合预期"，不能回答"**真实任务成功率是多少**"。
这个目录就是回答第二个问题的回路：一组小型真实任务（修 bug / 加特性 / 重构），
无头跑 minicode，按可执行校验判定通过，统计成功率、时长与 token。

## 指标口径（v0.22.1 固定，对比时必须遵守）

基线（eval/baselines/，13/13 = 100%）说明当前任务集对一线模型处于**饱和区**：
成功率的区分度有限，且会长期贴着 100%。因此版本间对比的口径固定为：

- **主指标：token 降幅 + 耗时降幅**（与 eval/baselines/ 基线对比，
  必须同模型、同端点、同 --timeout；基线：输入 553,437 / 输出 16,606 tok、
  平均 100.7s/任务）
- **护栏指标：成功率不低于基线**——回落即视为回归，先排查再谈收益

## 运行

```bash
python scripts/run_eval.py                # 全部任务（用当前环境变量的模型/端点）
python scripts/run_eval.py --filter json  # 只跑 id 含 "json" 的任务
python scripts/run_eval.py --timeout 240  # 单任务超时（秒，默认 300）
python scripts/run_eval.py --list         # 列出任务
```

模型配置与日常使用一致（`OPENAI_API_KEY` / `OPENAI_BASE_URL` / `OPENAI_MODEL`
或 `ANTHROPIC_*`）。结果打印 Markdown 友好表格并写入 `eval/results/eval-<时间戳>.json`。

## 任务格式（eval/tasks/*.json）

```json
{
  "id": "bugfix-off-by-one",
  "category": "bugfix",
  "instruction": "给智能体的任务指令（自然语言）",
  "setup": {
    "files": {"app.py": "初始文件内容…"},
    "commands": ["git init -q"]
  },
  "check": {
    "command": "{python} app.py",
    "expect_output": "10 20 30 40"
  }
}
```

- `command` 占位符：`{python}` = 当前解释器、`{check}` = `eval/checks/<id>.py`、
  `{sandbox}` = 任务沙箱绝对路径
- `expect_output` 可选：校验命令 stdout 必须包含该子串
- 复杂断言写成校验脚本放 `eval/checks/<id>.py`，以沙箱路径为 `argv[1]`。
  **校验脚本在沙箱外**，智能体改不到它，无法作弊。

## 新增任务的原则

1. 确定性：任何合格模型都能一次做对，断言不依赖环境
2. 小：初始文件 ≤ 40 行，指令 ≤ 3 句
3. 可作弊面为零：不把答案写进 setup 文件，校验逻辑放 checks/（沙箱外）

## 红队 precision 标注（v0.23）

只读红队（`/redteam`）的报告质量必须用数据说话，否则"红队有效"只是感觉。

```bash
python scripts/run_redteam.py --task bugfix-off-by-one   # 求解 → 红队 → 报告
python scripts/run_redteam.py --all                      # 默认 3 个标注任务
```

报告写入 `eval/redteam/<task>-<时间戳>.md`，内附空白三列表。标注流程：

1. **先盲标再看报告**：先自己读改动代码、列出自己看到的问题，再打开报告
   对照——否则"我也觉得对"会被锚定偏差误算成命中；
2. 三列：`红队提出的问题` / `是否真实存在(是/否/部分)` / `严重程度(阻断/应修/可选)`；
3. **"否"的条目最有价值**：它们直接度量红队提示词的误报率，决定 v0.24
   蓝队修复循环是否默认开启、攻击性强度要不要调；
4. **「存疑」条目单独统计**（不计误报也不计命中）：它们映射攻击面清单里
   "模型不确定"的风险类型——积累 5-6 个任务后，反复存疑且 eval 环境
   结构性不可测的攻击面（如编码环境/字节码缓存），应从提示词移出，
   转由 /review 或人工覆盖。

红队跑在"通过校验的正确解法"上——理论上无真问题；人工判"是"的发现说明
任务校验有盲区，同样是有价值的数据。

**第一批标注基线（2026-10-03，3 个简单任务）**：误报率 0%（1 条确定发现：
cli-flag 的字面量 `--upper` 被静默吞，红队比人工自查更具体；2 条存疑：
1 部分成立 / 1 不成立）。结论：提示词偏保守（"全无否"信号命中），但其中
两个任务天然无可发现缺陷，"无发现"是正确行为——**任务集过简，不足以判断
提示词上限**。v0.24 顺序据此调整为：先跑第二批中等难度任务
（`--batch2`：json-syntax / write-tests / implement-spec，红队能发挥的
场域）→ 据此校准提示词 → 蓝队循环等 precision 在中等难度站稳再上。
提示词已同步加入"先发散穷举可疑点、再逐条证伪"的工作方式要求。

## 蓝队 A/B 对照实验（v0.24.1，结论已落地）

第二批盲标后红队 go,但 A/B 实验（同一份红队报告,蓝队两种输入各跑一次）
给出了出人意料的结论：

| | 对照组 A（仅发现列表） | 实验组 B（全量含证伪过程） |
|---|---|---|
| 已知漏项覆盖 | 0/3（但"举一反三"补了 7 类 k 类型实例） | 0/3（补 3 类,且引入一处事实错误） |
| 证伪过程的影响 | 不受锚定 | **被带偏**:把"红队 diff 含 float() 但文件没有"归为红队瑕疵,未意识到评审对象与实际文件不同步 |
| 自验可信度 | 声称验证矩阵,**未实测**（项目无测试文件） | 声称"24 passed",**未实测** |

**结论：输入模式定稿 A（只读发现列表）**——覆盖面 ≥ B、成本更低、B 引入
事实错误。三个实验发现均已修复/落地：

1. **评审对象绑定**：`run_bluefix_ab.py` 红队对每轮求解**现场重跑**
   （旧报告评审的是另一次求解的产物——B 的"diff 含 float() 但文件没有"
   即此根源）；
2. **独立自验门**：蓝队自验命令必须以 ``- 自验: `<命令>` `` 格式声明,
   评测脚本**独立重跑**,PASS/FAIL 写进报告；未声明任何自验命令 = 自验
   缺失,数据不可信——两组蓝队的声明式自验都不可信,这是实验最重要的
   副产品；
3. **契约驱动提示词**：蓝队第 0 条硬要求——把 docstring/spec 每条承诺
   逐条对照实现（已兑现/未兑现/无法验证）。三个漏项（Decimal 精度/
   浮点容差/元素类型）都不是"已发现问题的同类",而是整条没人提过的
   契约——根因驱动的"举一反三"够不到,契约驱动才能补上。

**新指标：红队盲区率 = 红队漏项总数 ÷ 红队发现总数**。precision（0/31）
说明红队不乱说,盲区率（首批 pilot:3 漏项 vs 1 发现）说明红队说不全——
后者才指导提示词演进方向:结构性盲区（编码环境/字节码缓存/数值契约）
应从攻击面清单移到契约驱动检查里去。spec 模式同步把隐含契约显式化
（/spec new 起草提示已要求写出 元素类型/容差/边界语义）——给红队
可测的目标，比让它自己猜可靠。

**v0.25.1 验证跑（implement-spec findings,3 次尝试）**：v0.25 三个不变量
首次在真数据上验证——frontmatter 写入三作废值域各一（void:timeout /
void:no_selfverify / valid）、三态门在有效环境下判定、**归因首战命中**：
14 条单引号 `-c` 自验全部 SyntaxError,门 14/14 归因为"自验命令本身写错"
（零误判为"蓝队未修复"）,exit 码/traceback 末行/归因三件套齐备。超时调优：
600s 预算下 findings 成功率仍不稳定（1/3）,蓝队负载（契约驱动 + 自验矩阵）
需要更长预算或更多轮退避——已列为 v0.26 前置观察项。单引号问题已修：
蓝队提示词明令 `-c` 用双引号。

**契约驱动实测（v0.24.2）**：蓝队带契约清单后抓到了三个漏项中最关键的
"元素类型 float"（整条红队没提的契约，C2 → 未兑现 → 已修复）；浮点容差
被主动判为"契约未承诺,可接受"（合理豁免——契约沉默≠违反）;元素类型
校验仍漏（判例分歧,待更多样本）。结论：契约驱动有效但不完全,与
举一反三互补——举一反三扩展已知问题的覆盖,契约驱动扩展问题空间的维度。

## 数据可信性纪律（v0.24.2 起,先于任何新机制）

连续四轮的核心工作都是修 harness 而非加功能（二进制 null/sys.path/
diff desync/env 不一致/占位自验）——每加一环无头链路就暴露一类静默
失败。规则固化如下：

1. **独立自验门前置探针**：先验证 `python` 在门 env 里可达,不可达 →
   **整份报告作废**（环境问题属于 harness,不属于蓝队）,而不是把
   N 条环境性 FAIL 混进数据（首轮实战 6 条全 FAIL 即此）;
2. **自验缺失 = 数据不可信**：蓝队未声明 `- 自验:` 命令的报告,
   不进数据集;占位/示意命令按未通过计;
3. **失败必须响亮**：任何"门在 FAIL 而报告标通过"的组合都是缺陷,
   与 v0.23.4 的空报告同罪。

## 数据可信性不变量(v0.25 起,CI 强制)

"数据可信"不再是需要每次记得检查的属性,而是可强制的约束:

1. **harness 独占写入**:每份报告头部必须是可解析 frontmatter,
   `data_validity` ∈ {valid, void:timeout, void:env_unavailable,
   void:no_selfverify, void:json_parse, void:empty_result,
   void:pre_invariant}——**缺失即作废**(void:missing);
2. **CI 门禁**:`scripts/check_consistency.py` 扫描本目录与 eval/bluefix,
   任一报告缺失/非法 data_validity 即 CI 失败;
3. **门三态**:独立自验门输出 PASS/FAIL/**ERROR**——ERROR 是"命令没跑
   起来"(超时/无法启动),与 FAIL(跑了但结果不对)分离,避免环境性
   失败混进数据;FAIL 带 exit 码 + traceback 末行 + 归因(蓝队未修复
   vs 自验写错);
4. **超时退避**:无头调用超时自动 2× 重试一次(上限 600s);耗时与预算
   写入 frontmatter——能区分"模型变慢"与"机器变慢";
5. **作废不删数据**:作废报告一律保留(调参/排障证据链),只在统计口径
   排除。

**可见性**:`python scripts/data_audit.py` 输出有效率/作废率(按原因),
`--strict` 在缺 frontmatter 时非零退出。连续六轮的静默失败根因都是
"没有可见的失败率指标"——这个脚本让整类问题自动可见。

## 证据链说明

`eval/redteam/` 与 `eval/bluefix/` 是 A/B 判定与 precision 标注的
**证据链**（人工判定的依据,已入库）——它们不是可重现的度量,重跑
会因模型/采样不同而内容不同;`eval/results/`、`eval/baselines/` 才是
可重现度量输出（时间戳滚动,已 gitignore）。两者不要混淆。

**结果解读（小样本看方向，不看精确比例）**：默认 3 个任务的样本量下，
置信区间很宽，两个方向的阈值信号比精确数字更有决策价值——

- 3 个任务全无"否"（误报率 0）：警惕攻击性提示词**过于保守**，调激进
  一档后换 3 个不同类任务再跑（如 bugfix-json-syntax /
  feature-merge-dicts / refactor-extract-module）验证；
- "否"占比 > 40%：提示词**过度报警**，收紧攻击面清单后同样复跑验证；
- 介于两者之间：维持现状，累计更多标注再判。

另外：若报告出现「未覆盖区域」一节（diff 超过 14000 字符被截断），该任务
的 precision 单独定性，不并入总体数据。

## CI

`.github/workflows/eval.yml` 每夜（北京时间 02:00）自动运行，结果上传为
artifact。任务失败**不会**弄红 CI（eval 是度量，不是门禁）；配置
`EVAL_OPENAI_API_KEY` / `EVAL_OPENAI_BASE_URL` / `EVAL_OPENAI_MODEL`
secrets 后自动启用，未配置则跳过。

## 安全前提

任务以 `--yolo`（全自动）在临时沙箱目录运行——与 Codex / Claude Code 的
自动评测同一前提：仅在可信环境执行，不要在含敏感数据的机器上对不可信
任务集开 yolo。
